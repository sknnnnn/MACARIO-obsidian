# GXK12:2 — Arquitectura técnica

> Arquitectura técnica y modelo de datos del e-commerce de GXK. Se apoya en [[07 — Proyectos/GXK12.2/01 — GXK12.2 — Requerimientos|Requerimientos]] y [[07 — Proyectos/GXK12.2/02 — GXK12.2 — Arquitectura funcional|Arquitectura funcional]], no los redefine.

---

## 1. Objetivo

Definir el stack, el modelo de datos y los principios técnicos de GXK12:2, manteniendo la implementación modular para evitar acoplamiento innecesario entre el e-commerce y los proveedores externos.

---

## 2. Arquitectura general

```text
                ┌─────────────────────┐
                │     Tienda pública  │
                └──────────┬──────────┘
                           │
                           ↓
                ┌─────────────────────┐
                │      Next.js        │
                │ UI + Server Logic   │
                └──────────┬──────────┘
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
        ┌─────────┐   ┌──────────┐  ┌───────────┐
        │Supabase │   │ Mercado  │  │ Logistics │
        │ DB/Auth │   │  Pago    │  │ Providers │
        │ Storage │   └──────────┘  └───────────┘
        └─────────┘
```

Next.js es responsable de renderizado, navegación, UI, formularios, Server Actions/Route Handlers y de las operaciones sensibles del servidor. Las operaciones con información sensible o validaciones críticas nunca dependen exclusivamente del cliente.

## 4. Supabase

Cubre inicialmente: PostgreSQL, Auth, Storage, RLS y funciones/servicios server-side cuando corresponda.

### Storage

Las imágenes de producto se almacenan en Supabase Storage. El modelo separa producto, registro de imagen y archivo físico — no se guarda una URL directamente en el producto como única fuente de verdad. Esto permite reordenar imágenes, cambiar portada, eliminar y agregar múltiples imágenes.

## 5. Modelo de datos

### Categories

```text
categories
- id
- name
- slug
- description
- image
- sort_order
- is_active
- created_at
- updated_at
```

### Products

```text
products
- id
- category_id
- name
- slug
- description
- price
- status        (draft | published | hidden | discontinued)
- is_featured
- created_at
- updated_at
```

El producto no almacena el stock total como fuente de verdad: el stock real está distribuido entre variantes.

### Product Images

```text
product_images
- id
- product_id
- storage_path
- alt_text
- sort_order
- is_primary
- created_at
```

Relación: `products 1─N product_images`.

### Sizes

```text
sizes
- id
- name
- sort_order
- is_active
```

### Colors

```text
colors
- id
- name
- slug
- hex_code (opcional)
- is_active
```

### Product Variants

```text
product_variants
- id
- product_id
- size_id
- color_id
- sku
- price_override
- stock
- is_active
- created_at
- updated_at
```

Relaciones: `products 1─N product_variants`, `sizes 1─N product_variants`, `colors 1─N product_variants`.

La combinación producto+talle+color debe tener una restricción de unicidad apropiada para evitar variantes duplicadas. El modelo debe poder manejar productos que no necesiten todos los atributos.

### Outfits

```text
outfits
- id
- name
- slug
- description
- cover_image
- status
- starts_at
- ends_at
- sort_order
- created_at
- updated_at
```

### Outfit Products

```text
outfit_products
- id
- outfit_id
- product_id
- sort_order
```

Relación: `outfits N─N products`. No se duplican productos.

### Customers

```text
customers
- id
- name
- email
- phone
- created_at
- updated_at
```

Persisten para asociar pedidos aunque no haya cuentas tradicionales. No necesariamente tienen credenciales de login. Un mismo email puede estar asociado a múltiples pedidos.

### Orders

```text
orders
- id
- order_number
- customer_id
- status
- subtotal
- shipping_cost
- total
- shipping_method
- shipping_address
- lookup_token_hash
- lookup_token_expires_at
- created_at
- updated_at
```

`order_number` es independiente del UUID interno. El token de consulta no se almacena en texto plano: se guarda solo un hash seguro (si la arquitectura final lo permite).

### Order Items

```text
order_items
- id
- order_id
- product_id
- variant_id
- product_name
- variant_label
- sku
- unit_price
- quantity
- subtotal
```

Los campos de snapshot son centrales: si el producto cambia después, el pedido histórico sigue mostrando la información que tenía al momento de la compra.

### Payments

```text
payments
- id
- order_id
- provider       (mercado_pago)
- external_id
- status         (pending | approved | rejected | cancelled | refunded)
- amount
- currency
- raw_reference
- created_at
- updated_at
```

La implementación debe contemplar validación de webhooks y autenticidad de las notificaciones.

### Shipments

```text
shipments
- id
- order_id
- provider        (andreani | correo_argentino)
- service_type
- external_id
- tracking_number
- label_url
- cost
- status
- destination_type
- destination_data
- created_at
- updated_at
```

La estructura debe permitir agregar proveedores posteriormente.

## 7. Autenticación y RLS

El acceso administrativo puede apoyarse en Supabase Auth. La autorización separa claramente usuarios públicos de administradores. El acceso a operaciones administrativas está protegido tanto en frontend como en backend.

### RLS

- **Público:** puede consultar solo información pública (productos publicados, categorías activas, imágenes públicas, outfits publicados). No tiene acceso directo a stock interno detallado, clientes, pedidos, pagos ni información administrativa.
- **Administrador:** puede gestionar productos, variantes, stock, pedidos, envíos y outfits.

**Pendiente de validar:** políticas exactas, a implementar según la arquitectura de autenticación final.

---

## 8. Carrito

Puede vivir inicialmente en el cliente, almacenando `product_id`, `variant_id`, `quantity`. No debe confiarse en precio, stock ni total calculados en el cliente. Al iniciar checkout, el servidor recupera los datos reales.

---

## 9. Creación de pedidos (revalidación de checkout)

Antes de crear el pedido:

1. Recuperar productos.
2. Recuperar variantes.
3. Verificar que estén activas.
4. Verificar precios actuales.
5. Verificar stock.
6. Calcular subtotal.
7. Calcular envío.
8. Calcular total.
9. Crear/reservar pedido.
10. Iniciar pago.

Esto evita manipulación de precios o cantidades desde el navegador.

### Reserva de stock

```text
available stock
        ↓
temporary reservation
        ↓
payment
   ↙          ↘
approved     failed/expired
   ↓              ↓
confirm        release
```

La implementación debe impedir que dos procesos vendan simultáneamente la última unidad.

**Pendiente de validar:** duración exacta de la reserva.

## 10. Mercado Pago

La integración contempla: creación del proceso de pago, identificador externo, webhook, validación de autenticidad, consulta del estado real del pago, actualización de `payments`, actualización de `orders`, confirmación/liberación de stock según corresponda.

El retorno del navegador no se considera una confirmación definitiva del pago.

**Pendiente de validar:** configuración final de Mercado Pago y cuotas.

## 11. Seguridad

Principios:

- No confiar en datos del cliente.
- Validar precios server-side.
- Validar stock server-side.
- Validar pagos mediante webhook.
- Proteger endpoints administrativos.
- Usar RLS.
- No exponer UUIDs internos innecesariamente.
- Utilizar tokens impredecibles para consulta de pedidos.
- Mantener secretos únicamente en variables de entorno/server-side.
- Validar inputs.
- Controlar permisos.

## 12. Envíos

### Andreani / Correo Argentino — abstracción logística

```text
ShippingProvider

calculateRate()
createShipment()
generateLabel()
getTracking()
cancelShipment()
```

Implementaciones: `AndreaniProvider`, `CorreoArgentinoProvider`. Evita que la lógica de negocio quede atada a una única API.

**Pendiente de validar:** capacidades exactas de cada proveedor (API, condiciones comerciales, automatización) antes de cerrar la implementación.

## 13. Emails

```text
EmailService
├── sendOrderConfirmation()
├── sendPaymentConfirmation()
├── sendShippingNotification()
└── sendTrackingNotification()
```

### Consulta de pedido mediante token

Token impredecible asociado al pedido, sin derivarse de IDs internos, invalidable y con posible expiración (`lookup_token_hash`, `lookup_token_expires_at` en `orders`).

**Pendiente de definir:** proveedor de email transaccional.

---

## 14. Server-side boundaries

Lógica sensible centralizada en funciones server-side, agrupada conceptualmente en: Catalog, Cart validation, Checkout, Orders, Payments, Inventory, Shipping, Emails, Admin.

Las credenciales de terceros nunca se exponen al cliente.

---

## 15. Variables de entorno

Todos los secretos (claves de Mercado Pago, credenciales de Andreani/Correo Argentino, credenciales del proveedor de email, claves de Supabase server-side) deben mantenerse únicamente en variables de entorno del servidor, nunca en el cliente.

---

## 16. Auditoría técnica — integridad histórica

Los pedidos son independientes de futuros cambios del catálogo: `order_items` conserva snapshots de nombre, variante, SKU, precio y cantidad. Eliminar, ocultar o modificar un producto no altera el historial de pedidos.

## 18. Principios técnicos

- No confiar en datos del cliente para precio, stock o total.
- Confirmación de pago solo vía webhook validado.
- RLS como capa central de seguridad, no solo autorización de aplicación.
- Abstracción de proveedores externos (logística, email) para no acoplar la lógica de negocio.
- Snapshots históricos en `order_items` para preservar integridad de pedidos.
- Catálogo preparado para volumen alto: paginación, filtrado server-side, imágenes optimizadas, lazy loading, índices adecuados en PostgreSQL. No asumir que todo el catálogo puede cargarse en una sola consulta o página.
- Simplicidad en la v1, sin cerrar la puerta a: más administradores, más proveedores logísticos, más métodos de pago, cupones/promociones/descuentos, historial de stock, automatizaciones, analytics, integraciones externas, más tipos de contenido editorial. Nada de esto se implementa ahora.

---

## 19. Decisiones tomadas

- Stack: Next.js + Supabase (PostgreSQL, Auth, Storage, RLS).
- Modelo de datos por variante (no por producto) para el stock.
- Snapshot histórico de pedidos en `order_items`.
- Confirmación de pago exclusivamente vía webhook de Mercado Pago.
- Consulta de pedido sin cuenta mediante token hasheado, no ID interno.
- Abstracción de proveedores logísticos vía interfaz `ShippingProvider`.
- Revalidación completa server-side antes de crear un pedido (precio, stock, variante activa).
- RLS diferenciando público vs. administrador.

## 21. Orden recomendado de construcción

1. **Base:** Next.js, Supabase, Auth, Storage, RLS, estructura inicial.
2. **Catálogo:** categorías, productos, imágenes, talles, colores, variantes, stock.
3. **Tienda:** Home, catálogo, producto, carrito.
4. **Administración:** login, dashboard, productos, variantes, stock, outfits.
5. **Checkout:** datos, envío, revalidación, reserva de stock.
6. **Pagos:** Mercado Pago, webhooks, estados.
7. **Operación:** pedidos, emails, envíos, tracking.
8. **QA:** flujos de compra, stock, pagos, estados, seguridad, responsive, estados de error, QA visual.

Dependencias críticas a validar antes de cerrar el checkout productivo: integración actual de Mercado Pago, método concreto de checkout, webhooks y su firma/validación, estrategia de reserva de stock, API de Andreani, API de Correo Argentino, modalidades de envío, cotización, generación de etiquetas, tracking, proveedor de email.

## 23. Principio general

GXK12:2 debe construirse como un e-commerce real y operativo, no como un catálogo visual con funcionalidades agregadas posteriormente. La arquitectura prioriza: integridad del stock, integridad de los pedidos, seguridad, administración sencilla, escalabilidad del catálogo, separación entre frontend y operaciones sensibles, independencia razonable de proveedores externos, buena experiencia de compra y buena experiencia administrativa.

La dirección visual se define después, en Figma y con un sistema de diseño, sin alterar esta arquitectura salvo que el diseño revele una necesidad estructural real.
